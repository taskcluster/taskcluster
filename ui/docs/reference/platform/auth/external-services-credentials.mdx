The auth service has API methods for delegating access to external services such as AWS S3 or Sentry.
This functionality allows the exchange of Taskcluster credentials for corresponding external-service credentials.
For example, Taskcluster credentials can be used to control access to specific S3 buckets or even paths within those buckets.

The base credentials for these services are specified in the deployment configuration.
This ensures that they are closely guarded, but it also means that they are difficult to change dynamically.
As a best pratice, we recommend limiting use of these API methods to credentials that are widely useful in the deployment
For example, the Firefox-CI deployment provides credentials for AWS S3 buckets containing cached compiler outputs, that are used by most Firefox build tasks.

## Github repository tokens

The `auth.githubRepoToken` method allows a task to get a [Github App installation
access
token](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app),
limited to a set of repositories and permissions. It's meant to replace
personal access tokens stored in the secrets service: the resulting token is
short-lived (1h), isn't tied to a user and is much easier to audit as a token
request is entirely bound by the intersection of the task scopes and the application permissions.

The apps that can issue tokens are named in the deployment configuration, as documented in
[Cloud Credentials](/docs/manual/deploying/cloud-credentials).
Requesting `<permission>: <level>` on `<owner>/<repo>` through the app
`<appName>` requires the following scope with the owner and repository name in
lowercase:

```
auth:github-repo-token:<appName>/<owner>/<repo>:<permission>:<level>
```

Permission names and levels are mapped one to one with the [Github
API](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app).
Taskcluster doesn't widen its own scopes, a task holding `...:contents:write`
may only ask for `write`, even though the resulting token also allows reading.

### Example: cloning a private repository

Given a task with the [taskclusterProxy](/docs/manual/using/api#using-clients-in-a-task) feature enabled
and the scope `auth:github-repo-token:my-app/my-org/my-repo:contents:read`:

```bash
TOKEN=$(curl -s \
  --request POST \
  --header 'Content-Type: application/json' \
  --data '{"repositories": ["my-repo"], "permissions": {"contents": "read"}}' \
  "$TASKCLUSTER_PROXY_URL/api/auth/v1/github/my-app/my-org/repo-token" | jq -r .token)

git clone "https://x-access-token:$TOKEN@github.com/my-org/my-repo"
```

### Example: getting a token from python

The client libraries offer a wrapper around the same method, which is usually
more convenient when the token is used from a program rather than the shell.

Given a task with the [taskclusterProxy](/docs/manual/using/api#using-clients-in-a-task) feature enabled
and the scopes `auth:github-repo-token:my-app/my-org/my-repo:pull_requests:write` and `auth:github-repo-token:my-app/my-org/my-repo:contents:write`:

```python
auth = taskcluster.Auth({"rootUrl": os.environ["TASKCLUSTER_PROXY_URL"]})
token = auth.githubRepoToken("my-app", "my-org", {
    "repositories": ["my-repo"],
    "permissions": {"pull_requests": "write", "contents": "write"},
})["token"]
```

The same token authenticates any other github API call and can be used for
example with the `gh` CLI, or with a client library of your choice.
